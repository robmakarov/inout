# FLAGS — every switch in INOUT and its current default
Purpose: the current default of every URL flag / sticky setting and its measured effect. If a default moves, rewrite the row.
- This load only: append to the URL — `https://inout-kappa.vercel.app/?nativeres=1`.
- Sticky until changed: console `localStorage.setItem('inout.capture.nativeres', '1')` then reload.
- Precedence: URL > sticky > default. Only `?sourceframe=` STICKS when set from the URL.

## ON by default
| Switch | Turn it off with | What it does |
|---|---|---|
| **Quality step** `?qstep=` | `?qstep=540p\|720p\|1080p\|1440p\|max` | The slider above the input chips — the only quality decision (UI1, 2026-08-30). Default **1080p** (`inout.quality.step`). A CEILING binding both halves: capture asks for no more than that long edge (pixels above it are never encoded — the "save resources" saving) and the export ladder stops there (a step above what was captured could only be upscaled). Stamped on the take: a take opened from the list is capped by ITS step; a pre-UI1 take carries no step and keeps the ladder it was made under. `max` is what turns `?sourceres=` and `?sourcefps=` on — the screen's own resolution at 60 fps, nothing refused in advance. 1080p is the default because the composite is written at a 1920 long edge and the untouched export packet-copies it; a higher default would silently turn every export into a full re-render (pinned by test). |
| **Single generation** `?singlegen=` | `?singlegen=off` | A take with exactly one video channel already MP4/AVC at the geometry of the export step you picked: the export copies THAT channel instead of the composite or a re-render. Keeps colour (80.0 % vs 70.3 %), faster, 14–23 % more bytes. Since O3c (2026-08-29) it follows the SELECTED step — a native-res 1440p screen at the 1440p step is an instant copy, not a re-render; the panel badges such steps "Instant" and their size is the file, exact. |
| **Smart cut** `?smartcut=` | `?smartcut=0` | A trim-only edit copies packets instead of re-encoding — 12.7× faster, and the file is bit-identical to the untrimmed one. |
| **WebCodecs raw channels** `?rawcodec=` | `?rawcodec=mediarecorder` | Raw screen/camera recorded through WebCodecs instead of MediaRecorder (Robert's ruling 2026-08-26). 10× less audio-clock starvation, half the bytes at the same picture. |
| **Audio PCM tap** `?audiotap=` | `?audiotap=worklet` | Which tap carries a measured audio channel (mic / tab audio). `track` (default since A1): `MediaStreamTrackProcessor` reads PCM straight off the track — no AudioContext, no output-device clock, no render deadline to miss. `worklet`: the pre-A1 AudioContext + AudioWorklet path, unchanged, still the automatic fallback on any platform without the reader or without a sample rate on the track. Measured 2026-09-01 (`npm run exp -- tapstarve`, 180 s cells, one captured tab-audio track, every core busy): the worklet tap delivered 166.3 s and padded 13.6 s of silence for time its context never rendered; the track tap delivered 179.9 s and padded 0, and delivers SOONER (batch gap p50 3 ms vs 22.5 ms) — the sync anchor pays nothing. |
| **Composite engine v2** `?engine=` | `?engine=v1` | The worker compositor that owns its own encoder. v1 = the old MediaRecorder-on-canvas path. |
| **Native resolution** `?nativeres=` | `?nativeres=0` | Capture the screen at its own size instead of downscaling to 1080p — what makes the 1440p export step real detail instead of an upscale. Robert, 2026-08-29: "i need native resolution and 60 fps work, and not freezing, no turning it off." Capture is bounded at the LARGEST export step (2560 long edge, tied to QUALITY_TIERS by test), so nothing is captured that could never be exported. The freezing half is `?encoderbudget=`'s job. |
| **The recorder panel** `?panel=` | `?panel=0` | U1 — a Document Picture-in-Picture window that floats above every other app while a take runs: the timer, the audio ring, Stop and Pause/Continue. Its buttons make the SAME session calls the capture screen's own record button makes; there is no second way to end a take. Opened BY THE RECORD PRESS and closed with the take. The order inside that press is measured, not chosen (`node scripts/dpip-check.mjs`, Chrome 152): `requestWindow()` CONSUMES the click's transient activation and `getDisplayMedia` does NOT, so the screen request goes first and the panel second — reversed, the panel would spend the activation the screen needs and the take would die at the press. Chrome's picker survives the panel opening over it (the display promise was still pending 3 s later with the picker up). Costs the take nothing measured: a 15.2 s take with the panel open throughout graded GREEN, 10 of 10 dimensions in band, beside a `?panel=0` control of the same shape. The browser paints the title bar (34 CSS px on macOS Chrome, 0 on the other sides) with the origin string in it: no CSS reaches it, there is no icon API, and script can neither move nor resize the window. Off = exactly the app before U1, which is also what every browser without the API gets (Safari, any insecure context). |
| **All four inputs** | the chips on the capture screen | screen + camera + mic + system audio are all armed by default (`inout.capture.prefs`). |
| **Constant quality** `?cq=` | `?cq=off` | The export targets a QUALITY (H.264 qp20) instead of a bitrate. Measured at 1440p: ~11 % smaller at the same or better picture, on a still document and a scrolling one. `?cq=18` finer, `?cq=26` smaller. Only affects exports that RE-RENDER — an unedited 1080p export copies packets and never encodes. |
| **The frame follows the source** `?sourceframe=` | `?sourceframe=0` | ON EVERYWHERE since UI1 (2026-08-30, Robert: "no blackspace around" — he chose to move the OUTPUT, not only the preview, so the preview keeps predicting the export). The output frame takes the take's own aspect: a 1728×1117 screen exports at 1728×1117's shape instead of letterboxed into 16:9 (the bars were IN the file). Already on for phones before (camera-only, held portrait: 68 % of the picture thrown away by the landscape box). THE ONE SWITCH THAT STICKS when set from the URL (meant for a device with no console). Takes made under the old constant resolve to it too — `takeAspect` reads the composite the take actually wrote. |
| **The pressure detector** `?pressure=` | `?pressure=0` | The rate ladder reads leading signals four times a second from inside the compositor worker instead of judging `deliveredFps` (frames ALREADY lost): the video encoder's queue depth (the drop happens at 6, so depth = distance-to-loss), how long a frame sits in the encoder against the pipeline it can hold, that thread's scheduling lateness, and the synchronous cost per frame; worst signal wins and the step says which. Measured on Robert's machine 2026-09-01: the step lands 985 ms BEFORE the first lost frame (old ladder: 1972 ms AFTER it); recovery 576 ms after the load lifts (old: 3000 ms); no more climbing back INTO a load (old: down 17.0 s → up 24.0 s → down 27.0 s, all while loaded) — a take at the floor under pressure holds there. It refuses a step when the encoder is provably idle (queue 0.00/6, 15.9 ms latency, zero drops) = the SOURCE slowed, halving the rate fixes nothing. A step is still the rate only, never the size, never above the chosen step, never in `max` (ladder off there). Compute Pressure API and Long Animation Frames are NOT used: both silent in a hidden tab, which is every recording tab. Off = the ladder byte-for-byte as shipped. |
| **The pre-render** `?prerender=` | `?prerender=0` | The export is made before it is asked for (F16; since F16b it starts at STOP as well as in the editor). A take whose export must RE-RENDER (a max take with a camera: two video channels, nothing to packet-copy) starts that render the moment the take ends, and again 1.2 s after any edit settles; pressing Export JOINS the job, never restarts it. Measured 2026-09-02: a 16.7 s max+camera take's render finished 13.2 s after stop and the export took 14 ms. Every miss, failure, cancel or supersession falls straight through to rendering on demand. A take whose export is already instant (screen-only max, every sub-max take) never starts one. |
| **The crash floors** `?crashfloor=` | `?crashfloor=0` | H2b, two additive fixes (docs/CRASH_BOUND.md): (1) the pending manifest — the only pointer to a take's files until stop writes the row — also goes to an IndexedDB store with a real transaction commit (`durability: 'strict'`) beside the `localStorage` copy; Chrome commits localStorage asynchronously, and `kill -9` at 2.8 / 3.3 / 4.2 s recovered NOTHING while megabytes sat on disk. (2) The first video fragment closes at 1 s instead of at the 2 s GOP (one extra keyframe per take; every later fragment stays 2 s), so a take killed young salvages PICTURE, not audio alone (audio was already on ~1 s clusters). Off = salvage byte-for-byte as H2 measured; the 2.1 s steady-state bound is unaffected either way. |
| **The background brake** `?bgpace=` | `?bgpace=0` | Keeps the pre-render off a live take (Robert 2026-09-01: "render can be parallel to record, it just must not fuck up ... make it elastic too"). Reads the same pressure instrument as the ladder (`?pressure=`): nothing recording → full speed; a take recording and nominal → half the wall clock, worked in 100 ms chunks; fair → a fifth; serious or critical → fully paused, before the composite and before anything of the take's; a take whose pressure cannot be read is treated as strained. Climbs back one rung at a time after a second of quiet; a job fully shed for two minutes gives up rather than sit on the memory (the export then renders on demand). Off = a background render spends the machine exactly as before F16b — the positive control it was measured against. |

## OFF by default
| Switch | Turn it on with | What it does, and why it is off |
|---|---|---|
| **Capture-side single generation** `?singlegen=capture` | as written | Stops recording the composite at all — 45–49 % less written per second. Off because it gives up source-liveness detection ("your screen froze" stops being noticed). No preview cost: the preview falls back to the raw `<video>` in the same 16:9 contain-fit box, measured live on prod at ~1.8× the pixels of the compositor's 960×540 canvas (sharper). Only fires when the one video channel is exactly 1920×1080 — usually false with native resolution on, so on most machines it does nothing today. |
| **The rate follows the source** `?sourcefps=` | `?sourcefps=1` | Since UI1 this is what the `max` step means — on there, off at every step below; the flag is the override. The frame RATE takes THE SOURCE'S OWN, up to 60. What a take may attempt is MEASURED (2026-08-30): the app times its own video encoder once at load while nothing records, and a take gets 60 fps when its pixels-per-second fit that reading (the old rule refused 60 above a 2560 long edge — a cliff at 2559/2561 a freeze fell through, and it refused 60 at exactly the resolution `?sourceres=` delivers). No safety margin: the ladder measures the take as it RUNS and steps the RATE down when the machine is busier than at load. Capture stops asking every screen for `max: 30`; both engines paint and encode at the take's rate; the export steps carry it. Only ever UP — a 24 fps webcam still records 30; a source that offers 30 is unchanged to the byte. Off because F15's gate wants one real 60 fps take judged by eye before the default moves, and 60 fps = twice the frames ≈ twice the file. A take exports at the rate it was RECORDED at. |
| **The resolution step** `?resstep=` | `?resstep=1` | The screen's raw recording FOLLOWS a mid-take source size change (display resolution changed, shared window resized) by segmenting — F6's pause/resume machinery without the gap: the current file closes and the next opens at the new size on the same track. Without it: the encoder is configured once and Chrome scales every later frame back to the starting size = the upscaling bug. NOT a load ladder — under pressure the RATE moves, resolution never (Robert's rule). Costs a stepped take its own-resolution export (two segments, two geometries, nothing to packet-copy as one file); the composite's instant export is unaffected (one size throughout). Off because it changes the files a take produces. |
| **Your own resolution** `?sourceres=` | `?sourceres=1` | Since UI1 this is what the `max` step means (flag = override, slider = switch). Does NOTHING unless `?nativeres=` is on — otherwise the flat 1080p cap applies and a take can carry a settings line claiming it while its screen is 1080p (found 2026-08-30); the panel greys it out and the badge marks it INERT. Adds a **Max** export step = the screen's own long edge (3024×1964 instead of stopping at 1440p) and lifts the capture ceiling to match (one constant). Appears on any take bigger than 1440p whose SCREEN is one continuous channel (a `?resstep=1` take that changed size gets no step). A camera does not remove it (a PiP never sets the frame size) — it changes DELIVERY: screen-only = the packet copy, instant; with a camera = re-render from the raw channels at that size; the panel badges which. Also stops the composite being recorded at all on those takes (2026-08-30): the second hardware encoder is the difference between 481 Mpx/s and 356 on a 3024×1964 60 fps take. Costs (the ones `?singlegen=capture` carries): no source-liveness detection, the raw preview replaces the composited one (sharper), an export at a step SMALLER than the take re-renders instead of copying. |
| **The encoder budget** `?encoderbudget=` | **ON since 2026-08-30**; off with `?encoderbudget=0` | Robert: "non max video must stop fucking app record". The first thing it spends is the COMPOSITE, not the picture: over budget the composite is simply not recorded (a downscaled second copy of a frame the raw channel already holds; the third encoder that freezes a game tab in auto mode). Only if that is still not enough does it bound the SCREEN's capture size at arm time, before any encoder opens. A screen+camera take opens THREE encoders (raw screen, raw camera, composite); until O15 nothing added them up. Not a constant: the bound comes only from this machine's own history — a take that ran clean raises it, a rate-ladder step or a composite giving up lowers it, a take that worked outranks an older one that did not; a machine never seen to collapse has no budget at all, so nobody's first take is bounded. The re-render GPU-process crash is fixed (0f8fefe), so the cost of no composite is only that an unedited export re-renders instead of packet-copying. |
| **R128 loudness** `?loudness=` | `?loudness=r128` | Broadcast −14 LUFS normalization instead of the shipped p90 bounding. Off because R128 can only hit the target by turning takes DOWN; the shipped rule never attenuates. |
| **Loopback keeps its latency** `?looplat=` | `?looplat=0` | B13. The audio anchor subtracts the platform-reported input latency because a real capture device buffers sound before the page sees it. Chrome reports **10 ms for every audio track it hands out** (measured again 2026-09-02: the same `latency: 0.01` on a real mic and on a display-audio track), and tab audio is an internal loopback — no microphone, no device buffer. `?looplat=0` stops the subtraction on **loopback channels only** (`system-audio`); a mic keeps it under every setting. Worth **9.9–10.6 ms of lead** measured on the take itself (`node scripts/b13-tabaudio.mjs --looplat=both`, which reports `latencyContributionMs` — the part of the lead the subtraction put there, isolated from the picture's own spin-up). OFF because it changes where sound sits against picture, which Robert can hear, and the default moves on his yes and not on an argument. Every take now records `anchor.inputLatencyApplied` so a file says which way it was made. |

## Quality modes
| Switch | Example | What it does |
|---|---|---|
| **Capture quality** `?quality=` | `?quality=max` | `auto` (default): the machine is protected from the take — the rate ladder steps the frame RATE down under load and back as it eases; a rate the encoder measured itself unable to sustain is not attempted; with `?encoderbudget=1` a machine with a collapse in its history is bounded before anything opens; the SIZE never moves. `max`: nothing steps down and nothing is refused — the source's own resolution and rate for the whole take; there is no ladder in max (reachable with `?maxladder=1`, off by default); made to work by opening FEWER ENCODERS — at native resolution the composite is not recorded, so with more than one video channel the unedited export RENDERS (the price of max, paid at export time where a wait costs only time); source-liveness detection and the composited preview are off. |

## Test-only (never on a real take)
| Switch | Example | What it does |
|---|---|---|
| `?synthetic=1` | | Fake devices — no permission prompts. How agents drive the app. |
| `?slow=` | `?synthetic=1&slow=mic:6000` | DEAD CODE (G6e): `parseSlowChannels` has no caller; measured no effect. Wire it or delete it — until then nothing here delays an arm. |
| `?dead=` | `?synthetic=1&dead=camera` | The channel arms normally (track live, unmuted, correctly sized) and delivers ZERO frames for the whole take — B4's closed-lid camera, which wrote a 28-byte file. Video kinds only. |
| `?die=` | `?synthetic=1&die=mic:20000` | Ends a channel's track MID-TAKE, N ms after the record press (the Bluetooth mic that drops at minute 40, the unplugged camera). Stops the track AND dispatches `ended` — what a real unplug does and `track.stop()` alone does not. Any kind, comma-separated. |
| `?killenc=` | `?synthetic=1&killenc=screen:6000` | H1. A channel's ENCODER reports failure N ms after the record press, through the real callback (`new VideoEncoder({ error })`, or measuredAudio's `fatal`). The take contains it: segment closes, the next opens on the same live device, the seam is certified. Any kind, comma-separated. NOT gated on `?synthetic=1` — inducing it on a real screen share is the point. |
| `?killworker=` | `?synthetic=1&killworker=camera:6000` | H1. Kills a raw channel's WORKER N ms after the record press — it stops encoding and throws uncaught, the one thing that reaches `worker.onerror`. A different entry point from `?killenc=`, gated separately. Video kinds only (no audio channel has a worker). Name the same kind under both flags at different instants to exercise the containment budget. |
| `?slowstop=` | `?synthetic=1&slowstop=screen:9000` | H5. Holds a channel's STOP REPLY back N ms — the file is written normally, only the message saying so is late; the one thing `stop()` is bounded on (5 s), and the failure H1's rig hit under load (screen and camera missing from a take that had recorded them). Any kind, comma-separated. Milliseconds are measured FROM THE STOP, not from the record press. |
| `?quiet=` | `?synthetic=1&quiet=0.05` | Scales the synthetic audio down. |
| `?camsize=` | `?synthetic=1&camsize=1080x1920` | The synthetic camera's size (default 640×480) — a PORTRAIT take without a phone. |
| `?camlies=1` | `?synthetic=1&sourceframe=1&camsize=1080x1920&camlies=1` | The synthetic camera reports its dimensions TRANSPOSED — the one lie a real phone tells (`getSettings()` describes the sensor, the frames arrive rotated). The phone bug on a desktop. |
| `?screensize=` | `?synthetic=1&screensize=3840x2160` | The synthetic screen's size (default 1280×720). |
| `?screenfps=` `?camfps=` | `?synthetic=1&sourcefps=1&screenfps=60` | The synthetic screen's / camera's rate (default 30, max 120) — a 60 fps source without a 120 Hz monitor or a 60 fps sensor. |

## Not a URL flag — in the UI
| Setting | Where | Default |
|---|---|---|
| Quality ceiling | the slider above the input chips, before recording | **1080p** (`inout.quality.step`) |
| Export step | the same slider, under the timeline in the editor | whatever the take was recorded at; it can only go DOWN — steps above stay on the rail, greyed (those pixels were never captured). 1080p = the instant packet copy of the composite; since O3c (2026-08-29) a step matching the screen's own geometry is ALSO instant (screen-only takes: raw-channel copy, size exact); the Max step on a screen+camera take re-renders instead of copying; every other step re-encodes the whole take — slow and much bigger (export-size entry in `BACKLOG.md`). |
