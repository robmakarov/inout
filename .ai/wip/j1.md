## THE DESIGN (what the next session must not re-derive)
- CHUNK GRID = the OUTPUT timeline at multiples of gopSec (KEYFRAME_INTERVAL_SEC, 5 s),
  in exact output FRAME indices: chunk i = frames [i*gop*fps, (i+1)*gop*fps). gop*fps is an
  integer at 30 and 60, so the grid is exact and the concatenated file's frame timestamps are
  the unbroken render's own k/fps. No drift.
- CHUNK KEY = content, hashed (SHA-256 → `chunk-<hex>`). Content = recording id + settings +
  THE EDIT RESTRICTED TO THAT CHUNK'S OUTPUT SPAN: the source spans/speeds the span maps to,
  camera keyframes covering it (plus the bracketing pair), viewport keyframes covering it
  (plus bracket), background (global — a background change honestly invalidates every chunk),
  per-channel enable/trim for the video channels active in the span.
  Content-addressed ⇒ the cache IS the resume cursor: a chunk exists on disk only if it is
  complete, so a killed tab resumes at the last complete chunk with no journal to corrupt.
- AUDIO IS ONE ARTIFACT, NOT CHUNKS. Concatenating separately-encoded AAC/opus splices
  encoder priming into every 5 s boundary — an audible click every chunk. So audio is one
  continuous encode, cached under its own key = the AUDIO PROJECTION of the edit (segments,
  speeds, channel enable/trim, loudness mode, settings). A pure-pixel edit (zoom, camera,
  background) does not touch it ⇒ zero audio work on re-export. Proportional in KIND.
- CONCATENATION = packet copy (EncodedVideoPacketSource + EncodedAudioPacketSource),
  timestamps rebased by the chunk's output start. Every chunk shares one encoder config;
  the avcC description is BYTE-COMPARED across chunks exactly as smartCut does, and a
  mismatch falls back to the unbroken render.
- ONE READER SET PER CONTIGUOUS RUN OF MISSES. VideoChannelReader is strictly forward and
  its iterator is created lazily at the first sampleAt ⇒ open a fresh reader at each miss-run
  start (a seek), never skip forward through hits (that would decode them).
- THE CHUNK LOOP RUNS INSIDE THE EXPORT WORKER (export.worker.ts), not per-chunk workers:
  a new worker per chunk would pay worker start + first-VideoEncoder (~3.2 s, H6) per chunk.
- render.ts is FACTORED, not duplicated: prepare (readers/mixers/loudness/target/qp) is
  extracted; renderExport = prepare + one full window; the chunk loop = prepare once per
  miss-run + one Output per chunk. A second render implementation is forbidden (drift).
- SHIPS BEHIND `?chunked=` (default OFF until Robert's yes — FROZEN RULE). The unbroken
  render stays the runtime fallback for: waveform mode (audio-only take), avcC mismatch,
  OPFS unusable, any chunk failure.

## KNOWN AND STATED LIMIT (not a guess — a measurement-grade fact)
A TIME SHIFT (a cut/delete) moves every later chunk's output span onto different source
instants, and the shift is not generally a whole number of frames, so later chunks' pixels
genuinely differ at sub-frame phase. Exact reuse across a shift is not achievable; claiming
it would be the guess the ruling forbids. Pure TIME edits do not need this path at all —
they take smart cut. Where a shift IS a whole number of frames the content key hits for free.
